## D-010 Project JSON schema v1 interpretations (2026-11-16, T004)
Zod schema in `packages/core/src/schema/` (exported from `@nittcam/core`), modelled on spec §9.2. Where the spec is silent:
- **Strict objects:** unknown keys are rejected (no silent data loss); new fields arrive through a schema version + migration step.
- **Rect parts:** `params {w, h, r}` is the source; `outline` is optional and treated as a cache that is never read (`deriveOutline(part)` recomputes it). `r ≤ min(w, h) / 2`. The derived outline starts at `(r, 0)` (or `(0, 0)` when `r = 0`), runs CCW, uses quarter arcs with bulge `tan(22.5°)` and drops zero-length straight edges.
- **Contours:** `outline` and each `inners[]` entry are vertex arrays, implicitly closed. At least 3 vertices, or 2 when one segment is an arc (a circle). Direction (outer CCW, inner CW) is the stored convention but is not enforced by the schema; normalisation is T006's job.
- **Holes:** discriminated by `type`; every hole has an `id` (string, unique within its part, PO decision) so commands can address it. pocket = `id, d, cx, cy, depth, tool`; through = `id, d, cx, cy, tool` (no `depth`, it comes from stock thickness + machine sacrificial allowance, §4.5); groove = `id, d, cx, cy, depth, grooveWidth, tool`. For a groove, `d` is the **centreline** diameter (the tool centre follows that circle) and `grooveWidth < d` is required (PO decision). `tool` is the tool number in the machine profile (integer ≥ 1, PO confirmed). Rules that need other data (depth < thickness, d ≥ tool diameter, groove width vs tool) are validation rules for later tasks, not schema rules.
- **Enums:** `nesting.mode` ∈ `minWaste | fastest | minToolChanges` (§6.2); `cutting.leadIn` ∈ `arc | line`; `cutting.direction` ∈ `climb | conventional`; sheet `grain` ∈ `0 | 90` (free-angle grain is out of scope, §2.5); placement `rot` ∈ `0 | 90 | 180 | 270`.
- **Settings (§4.8, not in the §9.2 summary; PO decision):** top-level `settings.dimensionMode` ∈ `cut | finished`, default `cut` (a missing `settings` or `dimensionMode` parses as `cut`). In `finished` mode entered sizes are finished sizes and the edge-band thickness will be deducted from the cut size; only the field exists now, the deduction is implemented later.
- **Templates:** `params` is a record of number | string | boolean; `overrides` is the list of field names the user changed by hand.
- **Cross-references** checked by the schema: unique part ids; unique hole ids within a part; each placement points at an existing part, `index < qty`, and each copy is placed at most once. The grain rotation rule is enforced by the nesting engine, not the schema.
- **Migration:** `MIGRATIONS[n]` upgrades raw JSON from v`n` to v`n+1`; `parseProject(json)` upgrades then validates and returns `{ ok, project } | { ok: false, issues: [{ path, message }] }` (paths like `parts[0].holes[1].d`); `migrate(json)` throws `ProjectSchemaError`. Missing, non-integer or future `schemaVersion` is rejected with a clear message.
- **Dependencies:** `zod` 4.6.7 (MIT) in core, `fast-check` 4.10.2 (MIT) as a core devDependency.

## D-011 Command layer design (2026-11-16, T005)
Code in `packages/core/src/commands/` (registry, `plate/`, `part/`) and `packages/core/src/validate/`, exported from `@nittcam/core`. Spec §5.1, §5.4, §8.1.
- **Command = definition object:** `{ name, area, description, aiTool, params (Zod), check?, apply(draft, params) }`. `params` is the single source for runtime validation and the AI tool schema. Params objects are strict (unknown keys rejected).
- **Pure apply:** `applyCommand(project, name, params)` parses params, runs the optional precondition (`check`, e.g. duplicate part id), applies the recipe through Immer `produceWithPatches` and returns the new project plus forward and inverse patches. The input project is never mutated. The result is re-checked against `projectSchema`; a command that would produce an invalid project is rejected (`INVALID_RESULT`), so the stored project is always schema-valid. Rejections return `{ ok: false, error: { code, message, issues } }` and change nothing; codes: `UNKNOWN_COMMAND`, `INVALID_CONTEXT`, `INVALID_PARAMS`, `PRECONDITION_FAILED`, `INVALID_RESULT`.
- **Immer:** `immer` 11.2.9 (MIT, pinned; 11.2.10 was under two weeks old, D-008 rule). Core uses a private `new Immer({ autoFreeze: true })` instance so it never changes the global Immer config; `enablePatches()` is called once at module load. Projects returned by commands are frozen.
- **No clock in core:** the caller passes `{ actor: 'user' | 'ai', at }` with every command; `at` must be an ISO 8601 date-time with offset (validated by regex, not parsed). The log entry is `{ command, params, actor, at }` where `params` are the **parsed** params (defaults filled in), so replaying the log is deterministic.
- **CommandStack:** holds the current project, undo and redo stacks of `{ entry, patches, inversePatches }`, the append-only log and the current validation list. `execute` / `undo` / `redo` / `canUndo` / `canRedo`. Executing after an undo clears the redo stack. A rejected command touches nothing. Undo/redo are not log entries yet (open question; the `project_commands` table is T008+).
- **Ids are supplied by the caller** (`addPart.id`); core never generates random ids. `addPart` creates a rect part, appends it to `parts`, defaults: `name ''`, `qty 1`, `grainLock false`, zero edge band; inners/holes/templates empty. `addPart` params mirror the part JSON (`params: { w, h, r }`) so the `r ≤ min(w,h)/2` refine is reused.
- **Validation (rules, not schema):** `validateProject(project)` returns `{ code, severity, path, message }[]` and runs after every execute, undo and redo. The schema stays permissive (D-010). Rules now:
  - `PART_LARGER_THAN_SHEET` (error): rect part fits the raw sheet neither as is nor, when `grainLock` is false, turned 90°. Margin/gap are nesting concerns and not counted. Freeform parts are skipped until the arc-aware bbox (T006).
  - `HOLE_DEPTH_NOT_BELOW_THICKNESS` (error): pocket **and groove** depth must be `< stock.thickness` (§4.5). The "too close" warning needs a threshold the spec does not give (open question).
  - Hole diameter / groove width vs tool diameter (§4.5) is **not implemented**: the project has no tool table yet; it comes with the machine profile (T010).
- **AI tools:** `commandToolDefinitions()` returns `{ name, description, inputSchema }` for every command with `aiTool: true`, using `z.toJSONSchema(params, { io: 'input' })` (fields with defaults are optional). Refinements are not in the JSON Schema; `applyCommand` enforces them. Export and machine-profile editing are never AI tools (§5.4); `setMachine` only selects a profile and is allowed.

## D-012 Geometry core: bulge polyline (2026-11-16, T006)
Code in `packages/core/src/geometry/` (`constants`, `types`, `segment`, `polyline`, `transform`), exported from `@nittcam/core`. Spec §6.1, §4.4.
- **One vertex model:** `Vertex` is the schema type (`{x, y, bulge}`, D-010). `Polyline = { vertices, closed }`; `contour(vs)` wraps a stored (implicitly closed) contour. Segment i runs from vertex i to i+1; bulge = tan(θ/4), θ signed sweep, + = CCW. In an open polyline the last bulge is ignored.
- **Tolerances:** `EPS = 0.001` mm and `JOIN_TOL = 0.05` mm in `geometry/constants.ts`. One more constant, `MIN_BULGE = 1e-9`: smaller bulges are lines (sagitta < 5 nm on a 10 m chord; avoids a huge, imprecise circle). A zero-length chord is always a line. Core had no other magic tolerances to replace.
- **Segment helpers:** `arcOf` (centre, radius, start angle, sweep), `segmentMidpoint` (via the sagitta, no trig), `segmentLength`, `segmentArea`, `segmentBBox`, `sampleSegment`, `bulgeToSweep`/`sweepToBulge`.
- **Area:** exact for arcs: shoelace over chords plus r²(θ − sin θ)/2 per arc (series for |θ| < 0.01 to avoid cancellation). An open polyline is measured as if closed by a straight chord.
- **Orientation:** `'ccw' | 'cw' | 'none'`; |area| ≤ EPS² mm² is `'none'`. `normalize(poly, 'outer' | 'inner')` gives CCW/CW; open and degenerate polylines are returned unchanged (a copy).
- **Reverse:** a closed polyline keeps its start vertex (v0, vn−1, …, v1); each segment's bulge is negated and moved to the segment's new start vertex. For open polylines the ignored last bulge is carried along so reversing twice is the identity. Negation uses `0 − v` so no `−0` appears in output.
- **bbox:** endpoints plus the arc's axis extremes (0°, 90°, 180°, 270°) inside its sweep. Throws `RangeError` on an empty polyline.
- **Transforms:** `translate`, `rotate(poly, 0|90|180|270)` about the origin by swapping/negating coordinates (exact, no sin/cos), `mirror(poly, 'x' | 'y')` where `'x'` negates x (left-right flip) and `'y'` negates y. Mirroring negates bulges and flips orientation; it does not re-normalise (call `normalize`). `transform(poly, { mirror?, rotate?, dx?, dy? })` applies mirror → rotate → translate.
- **Closing (§4.4):** `isClosed` = flagged closed, or open with ≥ 3 vertices and ends within JOIN_TOL. `close` drops the duplicate end vertex (the previous segment now ends at the first vertex, bulge kept) and sets `closed: true`; a larger gap returns the open copy unchanged so the caller can warn "kesilemez, kapalı değil".
- **Wiring:** `PART_LARGER_THAN_SHEET` now covers freeform parts with the arc-aware bbox of `outline` (path `parts[i].outline`) and compares sizes with EPS slack (a bbox from arcs can overshoot an exact fit by rounding; rect parts get the same slack). Message sizes are rounded to 3 decimals. Margin/gap stay out (T012). `rectOutline` treats `r < EPS` as sharp corners (not machinable) and uses `sweepToBulge` for `QUARTER_ARC_BULGE`.
- **Tests:** unit tests per helper and fast-check properties on rectangles, rounded rectangles and convex polygons with bulges in [−0.15, 0.4] (inward arcs limited so they cannot cross at a ≥ 36° corner).

## D-013 Offset: our own TypeScript implementation (T007, PO decision, 2026-11-16)
Evidence: `docs/spikes/T007-offset.md`. Chosen: **C, our own arc-preserving offset in `packages/core/src/geometry/offset.ts`**.
- Why: as accurate as CavalierContours on every fixture and on 9 987 random contours (max deviation 2e-13 mm on fixtures); arcs stay bulges, so G2/G3 come out directly; 3.6 kB gzip, no runtime dependency, no second language (§8.4); does not inherit the 4 defects found in `cavalier-contours-js`. Clipper2 rejected: arcs come back only approximately (deviation above EPS) and its main repo is archived. Building Rust CavalierContours to WASM ourselves was rejected because it adds a second toolchain.
- `cavalier-contours-js` stays as a **devDependency test oracle only** (never in the bundle).
- API: in core, `offset(poly, d)` with d > 0 = right of travel. With stored orientations (outer CCW, inner CW), `+toolRadius` gives the tool-centre path for both. The toolpath layer (T014) exposes outer/inner semantics.
- `ARC_COLLAPSED` (corner radius < tool radius): a warning, surfaced to the user as a validation warning (§4.4) by the toolpath layer.
- `SPLIT` on an inward offset of an **inner contour or hole** is an **error that blocks export** (the tool cannot pass the neck, so the part stays attached). Implemented in the toolpath layer (T014). Safety first (§7).
- Known limits: single closed non-self-intersecting contour, no islands, worst case O(n²) (2000 segments ≈ 130–320 ms).
- Revisit triggers: pocket/island offsets, DXF contours with 1000+ segments, or a defect in C we cannot fix quickly.

## D-019 Rectangle placer, min-waste mode (2026-11-17, T012)
Code in `packages/core/src/nesting/` (`bins`, `nest`, `fit`, `tool`, `types`, `__bench__/`), the commands in `packages/core/src/commands/nesting/`, the size rule in `validate/`, and `apps/web/lib/nesting.worker.ts` + `use-nesting-worker.ts` + the parts page panel. Spec §6.2, §8.2, §5.1, §5.4.
- **Spacing formula:** spacing `s = (toolDiameter + gap) / 2`. Every part's bounding rectangle is inflated by `s` on each side for collision checks, so two parts are always at least `toolDiameter + gap` apart (each cut takes a kerf of one tool diameter around its part, plus the configured gap). The usable area is the sheet shrunk by `margin` on every side: `[margin, width − margin] × [margin, height − margin]`; a part (not inflated) must lie inside it. The packer works in a bin of `usable grown by s` (`x, y = margin − s`, `w = width − 2·margin + 2s`, `h = height − 2·margin + 2s`), so "inflated part inside the bin" ⇔ "part inside the usable area". The margin is therefore measured from the sheet edge to the part edge; the tool may run into the margin. Fits are accepted within `EPS` (0.001 mm), so separations and edges hold within EPS.
- **Tool diameter:** passed by the caller (`runNesting { toolDiameter }`, 0 < d ≤ 50 mm, same bound as the profile). `nestingToolDiameter(profile, stock)` picks the suggested tool of the profile's material set with the same material and thickness, else the largest flat/compression end mill, else the largest tool. The draft parts page uses the example profile (MDF 18 → T2, 8 mm) until the wizard selects a machine (T023).
- **Placement coordinates:** `(x, y)` is the bottom-left corner of the part's bounding box **after** rotation, in sheet coordinates (origin bottom-left, Y up). Rotation is about the part's local origin, CCW; the toolpath layer rotates the outline and translates its rotated bbox minimum to `(x, y)`. The placer emits `rot` 0 or 90 only (for a rectangle 180/270 have the same footprint); locked placements may carry any of the four.
- **Grain:** `grainLock` parts are never turned 90° (rot 0 only from the placer); free parts try 0 and 90 (squares only 0). The rule is relative to the sheet frame, so sheet `grain` 0/90 does not change it.
- **Algorithm:** own MaxRects (Jylänki; free list of maximal rectangles, split on placement, new pieces pruned against containing ones) with best-short-side-fit, best-area-fit and bottom-left, plus a guillotine bin (disjoint free rectangles, shorter-leftover-axis split) with best-short-side-fit and best-area-fit. Orderings: area, longest side, perimeter (w + h), height, width, all descending, ties by part id (code-unit order) then copy index. 5 orderings × 5 heuristics = 25 candidates. Each candidate packs copies in order, first-fit across open sheets (the best position on the first sheet that has one), and opens a new sheet otherwise. Freeform parts use the arc-aware bounding box of their outline (true-shape nesting later, §6.2).
- **Objective (§6.2):** `min(A_waste + λ·L_cut + μ·N_toolchange + ν·C_handling)`, weights `{ waste, cutLength (λ), toolChanges (μ), handling (ν) }` in `MODE_WEIGHTS` per mode, overridable per call. Only `A_waste` is measured now; L, N, C are 0 until the toolpath exists (T014+), so all three modes rank like min-waste for now and λ/μ/ν are placeholders. **A_waste** = for every sheet but the last, sheet area − part area; for the last sheet, the used strip − part area, where the used strip is the smaller of the full-height strip up to the rightmost part edge + s and the full-width strip up to the topmost part edge + s (the rest stays a reusable offcut). Candidates compare lexicographically: fewer unplaced copies, then fewer sheets, then lower objective; the earlier candidate wins a tie.
- **Locked placements:** `layout.sheets[i].placements[]` with `locked: true` stay on their sheet, unchanged and first in the sheet's list; they are inflated obstacles for the bins. Unlocked placements are recomputed. Sheets up to the last one holding a locked placement are kept (an earlier sheet without locked parts is filled like a new one). A locked copy is not placed again.
- **Unplaced:** a copy that fits the usable area in no allowed orientation is `TOO_LARGE` (checked before packing with the same rule as validation; packing is one pass per copy, so it always terminates). A defensive branch reports `TOO_LARGE` instead of leaving an empty sheet if a bin ever refuses an empty-sheet fit. Every input copy ends up placed once or unplaced once (property-tested).
- **Statistics:** part area = bounding-box area; sheet area = raw `width × height`; waste % per sheet and overall = 100 · (sheet area − part area) / sheet area; utilisation = 100 − waste. `summarizeLayout(project)` derives the same figures plus the copies with no placement from a stored layout (the UI uses it, so undo/redo update the numbers).
- **Validation:** `PART_LARGER_THAN_SHEET` now compares with the usable area (sheet − 2·margin) using the same `fitsUsable` rule as the placer, freeform parts by bbox (deferred from T005/T006). The message names the usable size and the margin.
- **Commands:** `setNestingOptions { mode?, gap?, margin? }` (at least one) and `runNesting { toolDiameter }`, both AI tools. The AI can run nesting but never passes placements (§5.4: the engine makes geometry). `runNesting` writes `layout` in one undo step; re-running with an unchanged result records nothing (`changed: false`).
- **Web Worker (§8.2):** `lib/nesting.worker.ts` runs `applyCommand(project, 'runNesting', …)` on the posted copy and returns `{ params, patches, inversePatches }` plus the summary. The page records them with the new `CommandStack.executeApplied(name, applied, context, basedOn)`: `basedOn` must still be the current project, otherwise `STALE_BASE` (the parts changed while nesting ran; the user re-runs); the patched project is schema-checked (`INVALID_RESULT`). So the placer runs once, off the main thread. The worker is created on first use and terminated on unmount.
- **Determinism:** no randomness, `Array.prototype.sort` (stable) with full tie-breakers, insertion-ordered free lists, first candidate wins ties; the result does not depend on the order of the input part list (property-tested, byte-identical JSON).
- **Benchmark:** `pnpm --filter @nittcam/core bench:nesting` (Vitest with `vitest.bench.config.ts`, not part of `pnpm test`) prints sheets, utilisation %, waste %, last-sheet use, winning strategy and median time for three datasets in `src/nesting/__bench__/datasets.ts`. Baseline (2026-11-17, 2800 × 2070, gap 8, margin 10, tool 8): kitchen cabinets 64 copies → 4 sheets, 75.28 %; shelf sets 27 copies → 2 sheets, 67.77 %; many small parts 300 copies → 2 sheets, 62.41 %. 200 random parts nest in well under 2 s in Node (≈ 40–100 ms).
- Revisit: when cut length / tool changes are measured (fill L, N, C and tune λ, μ, ν), offcuts first (§6.2, M4), best-fit across sheets or more heuristics if utilisation needs it, and true-shape nesting for freeform parts.

## D-021 Toolpath model: outer contour, multi-pass, leads, plunge, direction (2026-11-17, T014)
Code in `packages/core/src/toolpath/` (`types`, `build`, `path`, `lead`, `depth`, `safety`, `stats`). Spec §6.3, §6.1, §4.5, §7.1, §7.2; D-013, D-016, D-019.
- **Model:** `Toolpath { units: 'mm', frame: 'sheet', safeZ, clearanceZ, targetDepth, operations[] }`. An `Operation` (`outerContour` in M1) has the part/copy/sheet, tool number + diameter, rpm, feed, plunge feed, travel (`cw|ccw`), pass depths and ordered `segments` (`approach`, `leadIn`, one `pass` per depth, `leadOut`, `retract`). Moves: `rapid`, `plunge`, `linear`, `arc` (end point, centre `cx/cy`, `direction` cw = G2 / ccw = G3, `bulge`, feed). Every coordinate is absolute in the **sheet frame** (origin bottom-left, Z 0 = material top, negative down); a move starts where the previous one ended. No machine-origin or Z-zero conversion here (T017). An arc that changes Z is helical (ramps only). `operationMoves(op)` flattens the segments.
- **Tab hook (T015):** every pass is its own segment; the last one has `final: true`, so tabs are inserted into that move list only.
- **Outline in the sheet frame (D-019):** `deriveOutline` → normalised CCW → rotated about the local origin by `rot` → its rotated bbox minimum moved to the placement `(x, y)` (`placedOutline`).
- **Tool-centre path:** `offset(outline, +toolRadius)` (D-013). `ARC_COLLAPSED` → warning on the result. An outer offset that fails or is not exactly one loop → `OFFSET_FAILED` error. **Note:** an outward offset never collapses a convex corner (a rounded rectangle r 2 with tool r 3 gives corner radius 5, no warning); `ARC_COLLAPSED` on an outer contour comes from **concave** arcs smaller than the tool radius. Inner contours: hook `innerContourPath` (CW, `+toolRadius` into the opening): `SPLIT` → `INNER_SPLIT`, any `ok:false` → `INNER_OFFSET_FAILED`, both export-blocking. Inner contours and holes are **not cut in M1**: a part with them gets `INNER_CONTOURS_NOT_SUPPORTED` / `HOLES_NOT_SUPPORTED` errors (export-blocking instead of a file that silently misses features), plus the hook's errors.
- **Cutting parameters:** the profile's material set with the stock's material and thickness (`tool`, `feed`, `plungeFeed`, `rpm`, `stepDown` = pass depth), each overridable by `options.cutting`. None found and no complete override → `NO_CUTTING_PARAMS`. Tool not in the profile → `TOOL_NOT_IN_PROFILE`. Cut depth deeper than the tool's flute length → `DEPTH_EXCEEDS_FLUTE_LENGTH` (safety, the shank would rub). Non-positive or non-finite values → `INVALID_OPTION`.
- **Depth:** target = `−(thickness + zZero.spoilboardAllowance)` (§4.5). `n = ceil((total − EPS) / passDepth)` equal passes, pass i at `−total·i/n`, the last set to the target exactly (the EPS keeps 18.3 / 6.1 at 3 passes despite float rounding). Nothing goes below the target.
- **Start point:** the middle of the longest straight segment of the tool-centre loop (first one on a tie), away from corners; a loop without lines (circle) starts at its first vertex.
- **Direction:** CW spindle (M3) assumed. **Climb on an outer contour = CW travel around the part, conventional = CCW** (the offset loop is CCW; climb reverses it with `reverse`, which negates bulges so arcs keep their shape). Inner contours (later) are the opposite: climb = CCW.
- **Leads (§6.3):** `arc` = quarter arc of radius L tangent at the start point P on the waste side (lead-in from `P + L·n − L·t`, lead-out to `P + L·n + L·t`, n = outward normal, t = travel tangent); `line` = straight line of length L at 45° to the contour on the waste side; `none`. Default type = `project.cutting.leadIn`, L = tool radius. Clearance check: the lead's arc-aware box must lie inside the sheet rectangle extended by the contour's own path box (with margin 0 the contour itself runs outside the sheet); samples at most 0.05 mm apart must be outside every part, at least the tool radius (− EPS) from the own outline and at least the tool radius + 0.025 mm from every neighbour outline. The distance to an outline is 1-Lipschitz, so this half-step margin makes the neighbour check hold for the whole lead, not only at the samples (hardened after a 2 500-run fast-check flagged a lead close to a neighbour; the test checker's inside test for rounded rectangles was made exact at the same time). The own part gets no margin because the lead ends on the contour at exactly the tool radius. Fallback L, L/2, L/4, then no lead; warnings `LEAD_SHORTENED` / `LEAD_REMOVED`.
- **Plunge:** `straight` (default): plunge at the lead start to the first pass depth; deeper passes step down at P inside the existing kerf. `ramp`: plunge in the air to Z 0, lead-in at Z 0, then per pass a **zig-zag ramp** along the contour: forward over leg length L to half the step, back to P reaching the pass depth, then the full loop; so every pass starts at P. L = `length`, else `(step / 2) / tan(angleDeg)` (default 3°); clamped to the contour length with `RAMP_STEEPER`. **Every move that goes down in Z uses the plunge feed** (straight plunges and ramps); the cutting feed is never used going down.
- **Safe Z (§7.2 rules 2, 3; defence in depth):** each operation starts with a rapid at safe Z above the lead start, rapids down to the clearance height (default 2 mm above the material, clamped to safe Z with `CLEARANCE_CLAMPED`), plunges at the plunge feed, and ends with a rapid straight up to safe Z. XY rapids happen only at safe Z. `toolpathSafetyViolations` checks these rules plus the target depth, finite numbers, positive feeds and arc consistency on every build; a violation is a `SAFETY_VIOLATION` error (the post and reader check again).
- **Issues:** `{ code, severity, partId (null = project), message, copy?, sheet? }`; `ok` = no errors. Unplaced copies → `UNPLACED_COPIES` warning; nothing placed → `NO_PLACEMENTS` error.
- **Order:** by sheet, then placement order (simple and deterministic; replaced by the cut order of T016, D-023).
- **Summary (approximate):** cut length = 3D length of feed moves (helical length for ramps), rapid length = rapids within a sheet (the first rapid of a sheet starts at an unknown position and is not counted), time = feed lengths / feed + rapid lengths / `rapidFeed` (default 10 000 mm/min, no acceleration, tool change or warm-up).
- **Tests:** fast-check over random rectangular parts placed by the nesting engine and random options (lead type/length, straight/ramp, climb/conventional, tool, thickness, spoilboard, pass depth) with an independent checker (`toolpath.testing.ts`, own outline construction and the offset oracle's distance): cutting points at tool radius ± EPS, no move below target, no cutting move above Z 0, XY rapids at safe Z, descending moves at plunge feed, pass count/depths, travel direction, leads outside parts and inside the sheet, determinism. Hand example: 100 × 50, tool 6, 18 + 0.3, pass 6.1 → passes −6.1 / −12.2 / −18.3 on a 106 × 56 loop with r 3 corners.

## D-022 Tabs and small-part auto tabs (2026-11-17, T015)
Code in `packages/core/src/toolpath/tabs.ts` (+ `build.ts`, `safety.ts`, `path.ts#slicePath`). Spec §6.3, §2.4, §3.6; D-021.
- **Settings and precedence:** count, width, height. `options.tabs` > `project.cutting.tabs` (new optional `count`, `width`, `height`) > the material parameter set's new optional `tabs { count, width, height }` > `TAB_DEFAULTS` (count 4, width 10, height = min(3, thickness / 2)). Both schema changes are optional fields: existing profiles and projects parse unchanged, no schema version bump, no migration. Profile cross-check: `tabHeightAboveThickness`.
- **`cutting.tabs.auto`:** `true` = tabs on every part, placed automatically; `false` = tabs only on small parts. Small-part safety cannot be switched off.
- **Small parts (§6.3):** outline area < `smallPartArea` (default 50 000 mm² = 0.05 m²) **or** smaller bounding-box side < `smallPartMinSide` (default 100 mm); both configurable through `options.tabs`. A small part always gets at least 2 tabs (count raised to 2; one tab lets it pivot). With tabs off it still gets them, with one `SMALL_PART_AUTO_TABS` warning per part (not per copy); with tabs on there is no extra warning. **A small part with no room for 2 tabs is the export-blocking error `SMALL_PART_UNSECURED`** (per copy, `ok: false`; PO decision): M1 has no thin-skin fallback (M3) and an unheld small part can fly off the vacuum. The operation is still built so the UI can show it. Note: a ramp covering the whole loop (`RAMP_STEEPER`) leaves no room for tabs, so such a small part is blocked.
- **Width = bridge width.** The raised span on the tool-centre path is `width + D`: a centre at the target depth cuts everything within the tool radius, so the narrowest part of the bridge (the kerf middle) is the raised span − D = width. A raised span of just `width` would leave a bridge of `width − D` (none at all when width ≤ D).
- **Height = material left in the bridge** (PO decision; what the user types is what stays, as in VCarve). Tab top Z = `−(thickness − height)`, independent of the spoilboard allowance (600 × 400 example: 18 mm, h 3 → −15.0). Valid: `0 < height < thickness`, otherwise `INVALID_TAB`. Non-integer / < 1 count, non-positive width, negative or non-finite thresholds → `INVALID_TAB`. All export-blocking.
- **Which passes:** a pass at depth z gets the tabs iff `z < tabTop − EPS`, i.e. it is deeper than `−(thickness − height)`; a pass at or above the tab top never reaches the tab. The final pass (target −(thickness + spoilboard)) always qualifies. Examples, 18 + 0.3, passes −6.1 / −12.2 / −18.3: height 3 → top −15.0 → only −18.3 (−12.2 is above); height 10 → top −8 → −12.2 and −18.3. Same tab positions on every pass.
- **Placement:** on the tool-centre loop of the pass (starts at P, travel direction). A tab centre must be on a **straight** segment at least `width/2 + toolRadius` (= half the raised span) from both ends, so the raised span never touches a corner arc or a corner. Keep-out around P: the raised span stays outside `[0, max(leadOut reach, ramp leg) + r]` and `[total − (leadIn reach + r), total]`; lead reach = the lead's chord (a quarter arc and a 45° line stay within it). Tabs are spaced **exactly `total / n`** apart by arc length; the phase is the middle of the longest feasible phase interval (intersection over all n tabs of the allowed set; first one on a tie within EPS), which keeps every tab as far as possible from the forbidden zones. Neighbouring raised spans must not touch (`total / n > width + D`). No phase → try n − 1 … down to 1 (2 for small parts); fewer than requested → `TABS_REDUCED` (warning), none → `TABS_NOT_PLACED` (warning) on a normal part or `SMALL_PART_UNSECURED` (error) on a small part, per copy. "Prefer long straight segments" is met by placing only on straight segments; with exact spacing a rectangle gets one tab per side for n = 4.
- **Motion over a tab:** vertical rise to the tab top as a feed move at the **plunge feed** (rising is safe; plunge feed keeps it gentle and simple), the raised span at the cutting feed, then a vertical **plunge** at the plunge feed back to the pass depth. A step rather than a ramp: simpler, exact tab length and no descending move at the cutting feed. The pass segment still ends at P at its depth, so lead-out and the next pass's step-down are unchanged.
- **Model:** `Operation.tabs: Tab[]` (`centre/start/end` arc lengths from P, raised-span end points `x0,y0,x1,y1`, `z`), empty when none. Tab moves stay inside the `pass` segments.
- **Safety checker:** adds: tab tops strictly between target and Z 0; no feed move above Z 0; a vertical move down must be a `plunge` (plus the existing rule that every descending move is at the plunge feed, and nothing below the target).
- **Tests:** `tabs.test.ts`: fast-check (random nested rounded rects, random count/width/height/auto, leads, straight/ramp) against an independent loop description: raised spans on one straight edge clear of corner arcs (XY on the path at tool radius ± EPS), raised span = width + D, Z exact, target elsewhere on the final pass, count or reduced with warning, spacing = total/n (± EPS; the independent loop length differs by ~1e-4 for near-zero corner radii), drops are plunges at plunge feed, every pass below the tab top flies the tabs, determinism; plus the T014 checker on the same results. Hand cases: 600 × 400 (positions below), 80 × 80 auto tabs, precedence, deeper passes, INVALID_TAB, SMALL_PART_UNSECURED, schemas. Changes to T014 tests: `SMALL_PART_AUTO_TABS` filtered out of exact warning lists (their 100 × 50 parts are small now); the random-project properties (`toolpath.property.test.ts` and the tester's walker `toolpath.safety.test.ts`) accept `SMALL_PART_UNSECURED` as the only error (tiny parts with big tools); the ramp-clamp case expects it and checks the ramp with the small-part rule off.
- **Hand example:** 600 × 400 at (100, 100), tool 6, 18 + 0.3, arc lead 3, climb, 4 × w 10 h 3: P = (400, 97); phase = (3√2 + 203)/2 = 103.621; tab centres (296.379, 97), (97, 403.621), (503.621, 503), (703, 196.379); spacing (2000 + 6π)/4 = 504.712; Z −(18 − 3) = −15.0; only the −18.3 pass flies them (−12.2 is above −15.0).
- Revisit: thin skin instead of tabs (M3, §2.4), tabs on inner contours, manual tab positions, a ramped tab profile if the step marks the edge, tabs inside a ramp zone (clamp the ramp over the tab) so small parts with long ramps are not blocked.

## D-023 Cut order and rapid ordering (2026-11-17, T016)
Code in `packages/core/src/toolpath/order.ts` (+ `build.ts`, `path.ts#startEdgeCandidates/startAtEdge`, `types.ts`), bench in `src/toolpath/__bench__/order.bench.ts`. Spec §6.3, §6.2, §4.5; D-021, D-022. Replaces the T014 order (sheet, then placement order).
- **Abstract items:** the order works on `OrderItem { sheet, part (copy key), cls, tool, area, starts[] }`, so the rules already hold for kinds M1 does not cut (drill/pocket/groove = holes of §4.5, inner contours) and for several tools; tests feed such fake items. In M1 the builder creates one outer-contour item per placed copy with the profile's tool.
- **Hard constraints (all modes):** each sheet is its own program (sheets ascending, never mixed). Within one part copy: holes/pockets/grooves → inner contours → outer contour (cutting the outer first frees the part). Outer contours in **non-decreasing outline area** (small parts first while the vacuum is strong, §6.3); area = the part's local outline area (rotation-free, so identical copies tie exactly), exact comparison; equal areas are free and tie-broken by distance. In `minToolChanges` the area rule holds only between outer contours of the **same tool**.
- **Greedy list schedule** per sheet: among the ready items (all predecessors cut) pick by key: current tool first (tool grouping), class (holes 0, inner 1, outer 2: the global class order where it does not conflict with a tool group), area (outer), distance from the tool's position to the item's nearest start point (nearest neighbour; the tool starts at the **sheet origin**), input (placement) order. A tool change happens only when no ready item uses the current tool; the next tool is the best ready item's ("first needed tool"). Property: at every tool change no item of the old tool was ready.
- **Start points:** every item offers candidate start points; a contour ends where it starts (the lead-out end is within a lead length of it, ignored in the measure). For a fixed order the best candidates are chosen **exactly by dynamic programming** (Viterbi, O(n·k²)), not greedily. Outer contour candidates = midpoints of straight edges of the tool-centre loop: **`minWaste` / `minToolChanges`: the longest straight edges** (ties within EPS; T014's rule, so a single part keeps its T014 start, e.g. the bottom edge of a rectangle seen from the origin); **`fastest`: every straight edge ≥ 0.5 × the longest** (`FASTEST_START_EDGE_FRACTION`). A midpoint of a straight edge is always away from corners and arcs. The start is chosen **before** leads and tabs are computed: the builder rotates the loop to the chosen edge, then runs the unchanged T014/T015 lead and tab placement for it, so every lead clearance, tab keep-out and safety rule holds as before (the lead fallback L, L/2, L/4, none still applies; the order does not prefer an edge with more lead room).
- **2-opt:** segment reversal inside **runs** of consecutive items with the same tool, class and (outer) area. Any permutation of such a run keeps every constraint (no precedence links items of equal class and area; the done-set at run borders is unchanged), so the pass can never break one. First improvement, improvements below 1e-9 mm ignored, bounded by an evaluation budget per sheet (`CUT_ORDER_DEFAULTS.maxEvaluations`: minWaste 20 000, fastest 100 000, minToolChanges 20 000; `options.order.maxEvaluations` overrides, 0 = off; a non-integer or negative value is `INVALID_OPTION`). The pass starts from the shorter (DP-evaluated) of the greedy tour and the naive one.
- **Measure and report:** `ToolpathResult.order { mode, placementRapid, naiveRapid, rapid, toolChanges }`, rapid = XY distance from the sheet origin through every start point, summed over sheets. `placementRapid` = T014 order with default starts (reference only: it ignores the rules); `naiveRapid` = the rule-abiding order with ties by placement order and default starts. Guarantee (property-tested): `rapid ≤ naiveRapid`, since the DP is optimal for any fixed order and the 2-opt only accepts improvements. `summary.rapidLength` (D-021, actual rapid moves within a sheet) is unchanged and follows the new order.
- **Modes (§6.2), ordering only, nesting unchanged:** `options.order.mode` > `project.nesting.mode`. `minWaste` = the default rules above; `fastest` = more start edges and a larger 2-opt budget (shorter rapids, same safety rules); `minToolChanges` = tool groups first, small-first only within a tool. The small-before-large rule is **not** relaxed in `fastest`: it is a vacuum safety rule (§6.3).
- **Issues** stay in placement order whatever the cut order (each copy's warnings/errors are buffered and appended in placement order). `SMALL_PART_AUTO_TABS` (once per part) is attached to the first copy cut.
- **Determinism:** no randomness; full tie-breakers (input order last); byte-identical results property-tested.
- **Tests:** `order.test.ts` (fast-check over random parts of mixed sizes on up to 3 sheets with fake holes/pockets/grooves/inner items on 1–3 tools, all modes, checked without the module's helpers: permutation, sheets ascending, within-part order, area order, tool grouping, reported rapid/tool changes = independent sums, `rapid ≤ naiveRapid`, 2-opt never longer, deterministic; hand cases: 3 parts in a row → small, medium, large; holes on T1 + outers on T2 → exactly one tool change; global class order; minToolChanges blocks; nearest neighbour with start choice). `toolpath.order.test.ts` (random nested projects through `buildToolpath`: permutation of placements, small first per sheet, rapid ≤ naive, the T014 checker `toolpathViolations` clean, start on an allowed edge midpoint, deterministic; hand: small/medium/large, single part keeps the T014 start in minWaste, fastest picks the nearer short edge). The tester's walkers `toolpath.safety.test.ts` and `toolpath.tabs.safety.test.ts` pass unchanged.
- **Bench** (`pnpm --filter @nittcam/core bench:order`, 2800 × 2070, tool 8; rapid in m: placement order / naive rules / optimised): kitchen cabinets 64 ops: 57.30 / 71.35 / **48.45** minWaste (−32.1 % vs naive), **45.79** fastest (−35.8 %); shelf sets 27 ops: 19.66 / 23.46 / 11.00; many small parts 300 ops: 283.19 / 337.19 / 319.28 minWaste, 306.82 fastest (300 distinct areas leave few ties, so the small-first rule dominates). Build time incl. the order ≈ 10 ms (kitchen), ≈ 210 ms (300 parts).
- Revisit: real hole/pocket/inner operations (they plug in as items), several tools in M1+ (tool per operation), counting the lead-out end and the park move in the measure, Or-opt moves, preferring start edges with full lead room, area bands instead of a strict area order if the owner wants shorter rapids in `fastest`.

## D-025 Post processor: declarative config, one generator, frame conversion, golden files (2026-11-17, T017)

- **Config (`postConfigSchema`, `schemaVersion: 1`, strict):** `id`, `name`, `version` (x.y.z), `status` (`unverified|verified`), `program {prefix, start, end, suffix}` (raw printable-ASCII lines), `comments {style paren|semicolon, asciiOnly, maxLength}`, `lineNumbers {enabled, start, increment, max}` (wraps to start above max; N only on blocks, not on comments or `%`), `modal.words`, `toolChange {mode auto|manual|none, manualStop M0|M1, lengthOffset, pauseForFirstTool}`, `spindle {on, off, speedPosition after|before, rpmDecimals}`, `dwell {word P|X, unit s|ms, decimals}` (rounded **up**, a dwell never gets shorter), `motion {G0/G00 …, suppressRepeatedCode, suppressUnchangedAxes}`, `decimals {xy, z, arc, feed}`, `arcs {enabled, mode ijIncremental|ijAbsolute|r, distanceModeWord G91.1|G90.1|null, fullCircle, helical, maxSweepDeg, chordTolerance}`, `drill.cycles none|G81|G83` (hook only: M1 has no drill operations; any operation other than an outer contour is refused), `vacuum.enabled` (the codes come from the profile), `file {extension, maxNameLength, lineEnding crlf|lf, maxSizeBytes, onOversize split|error}`. **Schema-level safety:** the modal words must contain G21, G90, G17, one of G54–G59 (rule 1) and the declared arc distance word, and no G20/G91/G18/G19/G93/G41/G42/G43 or duplicates; absolute I/J needs G90.1; R mode forbids full circles and more than 179° per block (R is ambiguous near 180°); `program.end` must contain M30 or M2 (rule 7).
- **Profile vs config:** the profile's constraints can only make the output more conservative: arcs = config **and** profile; line numbers = config **or** profile; name length and file size = the smaller limit. Tool change: an `auto` post (T.. M6) on a profile whose changer is not `auto` is refused (`TOOL_CHANGE_UNSUPPORTED`), since M6 on a machine without a changer is unsafe; `manual` and `none` posts work with any changer. `G43 H<tool>` only when both the config's `lengthOffset` and the profile's `lengthCompensation` are on. Post binding: the profile's `post.id` must equal the config id and the versions must match after normalising (`1.0` = `1.0.0`), else `POST_MISMATCH`. `KNOWN_POSTS` in core lists the shipped ids/versions for the machine form (the web app does not depend on `@nittcam/machines`); a test checks it against the JSON files.
- **Signature:** `generateGcode(toolpath, { profile, version, verification }, postConfig, meta { projectName, revision, stock {material, thickness, sheetWidth, sheetHeight}, fileStem? }, { check? })` → `{ ok, files [{ name, content, sheet, tool, part, parts }], errors, warnings }`. Config and profile are validated again inside. The meta thickness must match the toolpath target depth (−(thickness + allowance)), else `STOCK_MISMATCH`. Any error → `ok: false` and **no files**.
- **Frame conversion (only here):** sheet frame = origin at the sheet's bottom-left seen from the machine front, X right, Y back, Z 0 = material top. Program zero sits at `origin.corner`; the sheet corner nearest to it is `sheetOffset` mm from it, measured into the table. Physical offset of a sheet point from zero: `dx = x + (zero on the left ? off.x : −(off.x + W))`, `dy = y + (zero at the front ? off.y : −(off.y + H))`; machine `X = (xPositive right ? 1 : −1)·dx`, `Y = (yPositive back ? 1 : −1)·dy`; `Z = z` (Z zero = material top) or `z + thickness` (Z zero = table). Exactly one mirrored axis swaps G2/G3 (I/J come from the mapped centre, so they follow). An axis pointing away from the table gives negative coordinates: allowed, with the warning `AXIS_AWAY_FROM_TABLE`. **Safe Z is always above the material top:** the toolpath's safe Z is in the sheet frame, so with Z zero = table it is written as safeZ + thickness (safe side; the profile's "safe Z above Z zero" is read as above the work). **Worked examples** (sheet 1000 × 500, offset (10, 20), t 18): front-left, X+ right, Y+ back, material top: (0, 0, 0) → (10, 20, 0). Same with Z zero = table: final pass z −18.5 → −0.5 (0.5 into the spoilboard), safe Z 20 → 38. Back-right, X+ left, Y+ front: (0, 0) → (1010, 520); (1000, 500) → (10, 20). Front-right, X+ left, Y+ back: (0, 0) → (1010, 20), mirrored, so a CW arc becomes G3.
- **Envelope (rule 6):** program zero is taken as a corner of the travel. Every endpoint and every arc's quadrant extreme points must lie within `workEnvelope.x/y` of zero, measured into the table, and between `spoilboardAllowance` below the table surface and `workEnvelope.z` above it (the safe Z too). Out → `OUT_OF_ENVELOPE`.
- **The ten rules in the generator:** (1) the schema-guaranteed modal line is written first, plus a final text check of the program; (2) the first motion is `G0 Z<safe>` (always written in full); an XY rapid needs the current and the target Z at safe Z (`RAPID_BELOW_SAFE_Z`); a feed move from an unknown position is refused; a toolpath safe Z below the profile's is refused (`SAFE_Z_INVALID`); after an auto or manual tool change XY becomes unknown and safe Z is written again; (3) a rapid ending at or below Z 0 → `RAPID_INTO_MATERIAL`; every descending feed move must be at most the operation's plunge feed (`PLUNGE_TOO_FAST`); (4) `M3 S<rpm>` + `G4` warm-up before the first feed move, again after every tool change or rpm change; rpm outside the spindle range → `SPINDLE_INVALID`; a 0 s warm-up writes no dwell and warns `NO_WARMUP`; an internal guard refuses a feed move while the spindle is not ready (`SPINDLE_NOT_READY`); (5) feeds must be finite and > 0 (`FEED_INVALID`); F is **always** written on the first feed move after any rapid, plunge, spindle start or tool change, otherwise omitted when unchanged; (6) above; (7) the end is `G0 Z<safe>` **once** (skipped when the last motion was already a Z-only rapid to safe Z, i.e. the toolpath's retract; written when it was not), spindle off, vacuum off (profile code), the config's end lines; vacuum on without an off code → `VACUUM_OFF_MISSING`; (8) `formatFixed` = `toFixed` + checks, throws on NaN/Infinity/|v| > 10⁷, writes `-0.000` as `0.000`; a throw becomes `NUMBER_INVALID`; inconsistent arcs (radius mismatch > 0.002 mm, bulge sign against the direction, end point against the sweep) → `ARC_INVALID`; (9) the `options.check` hook: any error from it refuses the result (`CHECK_FAILED`); blocking the download is T019/T021; (10) the header line "DOĞRULANMADI, önce air cut" ("DOGRULANMADI, once air cut" when ASCII-only) comes **first** whenever the profile state is not `verified`, the profile is an example, or the post is `unverified`.
- **Generic post, rule-1 exception (arc distance mode):** the generic post writes no G91.1. Fanuc-type controls reject G91.1 with an alarm, I/J incremental is the RS-274 default on every common controller, and the generic post is `unverified` until it is adapted to the real controller (field test 1, a new post version with golden files). The generator checks the arc word only when a config declares `arcs.distanceModeWord` (Mach3: G91.1, written explicitly).
- **Z rounding toward +Z (PO decision on PR #25, T019):** every Z word (moves, safe Z) is written with `formatFixedUp`: rounded up onto the decimal grid (a value within 10⁻⁶ of a grid step snaps to it, so float noise such as −12.199999999999999 stays −12.200), so a written Z is never deeper than the model and never a full unit above it (−3.1635 → −3.163, not −3.164 below the spoilboard allowance). XY keep normal rounding; I/J keep arc consistency (the reader's radius tolerance covers it). Machine +Z is always up, so this holds for both Z references. The golden files were regenerated with it: byte-identical (their depths are exact). Property test `post.zround.test.ts`: random values (written ≥ value, < value + 1 unit) and random thickness/spoilboard/pass depth through the generator (no read Z below the target, pass depths never deeper). The tester's walker `post.safety.tester.test.ts` compares Z within one unit (was 0.6) accordingly.
- **Arcs:** I/J (and R) are computed from the start **as written** (rounded), so the controller's centre is within 0.0005 mm per axis of the true one. Arcs longer than `maxSweepDeg` are split evenly; full circles are split in halves unless `fullCircle`; `arcs: false` (config or profile), or a helical arc with `helical: false`, becomes lines with sagitta ≤ `chordTolerance` (at most 90° per segment). Arcs always write X and Y.
- **Header (§6.6), no timestamps** (byte-deterministic; the date lives in the export record, T021): the unverified line, project, revision, post id/version/name (+ "DOĞRULANMADI"), profile name + version, verification state (Turkish label, "ÖRNEK PROFİL" for examples), sheet n/N (+ part k/K), material/thickness/sheet size, origin corner/axes/offset, Z zero reference, tools, "NittCam ile üretildi". - **Files:** one program per sheet (D-023); in `none` mode one per consecutive tool run (`_T<n>`, a repeated run `_T<n>_2`). ## D-026 G-code reader: independent lexer, modal machine, arcs, lint boundary (2026-11-17, T018)
Code in `packages/core/src/gcode-reader/` (`lexer`, `reader`, `arc`, `comparable`, `types`). Spec §6.5, §7.2; gcode-safety skill. Written from `main` before T017 (D-025) was merged, on purpose; nothing from `src/post` is imported or copied.
- **Independence (§6.5, safety property):** the reader imports nothing outside its folder except `../geometry/constants` (EPS). Enforced in `eslint.config.js` for `packages/core/src/gcode-reader/**` (the core purity patterns are repeated because flat config replaces rule options per file): `no-restricted-imports` rejects **any specifier with a `..` segment anywhere** (`../x`, `./../x`, `./a/../../x`, and backslash spellings) except exactly `../geometry/constants` (the folder has no subfolders, so every `..` leaves it; roundabout spellings of the allowed file are rejected too), absolute paths (`/`, `C:`, `file:`), `@nittcam/*` and `module`/`node:module` (`createRequire`); `no-restricted-syntax` rejects the forms `no-restricted-imports` cannot see: dynamic `import()`, `require()` / `x.require()`, `import x = require()` and `typeof import()` types. The reader needs none of them. `independence.test.ts` (1) parses every file of the folder with the TypeScript parser, finds every module reference in all those forms, **resolves** relative specifiers against the folder and requires them to stay in the folder or equal `geometry/constants` (packages: a short tooling list), and rejects every dynamic form; (2) probes the ESLint rules with `lintText` (static, dot-slash, roundabout, barrel, absolute, require, dynamic import, import-equals, import types). The tester's probe `post/reader.independence.tester.test.ts` covers the same from outside the folder. Tester round 1 (B1/B2): `./../post/generate` passed the first regex and the scan, and `require`/`import()`/`import =` were not covered; fixed as above.
- **API:** `readGcode(text, options) → { ok, moves, events, lines, errors, warnings, lineEnding, finalState }`. Never throws on text; `ok` = no errors. Exported names are prefixed (`GcodeMove`, `sampleGcodeMove`, `gcodeMoveLength`, `sameGcodePoint`, `lexGcodeLine`) because the core barrel already exports toolpath names (`Move`, `moveLength`).
- **Frame:** millimetres in the **program frame** (coordinates as written, relative to the active G54–G59 offset; the offset values are unknown here). Converting to the sheet frame for comparisons is T019's job (it knows the profile's origin and Z zero).
- **Lexer:** words = letter + number, case-insensitive, whitespace optional (also between letter and number); numbers `[+-]digits[.digits]`, leading zero optional (`.5`, `5.`). `( … )` comments (no nesting; unclosed = `UNCLOSED_COMMENT`), `;` to end of line, `/` block delete at line start, `%` markers. **Exponents (`1e3`, `1.5E-2`) = `EXPONENT_NUMBER` error**; a letter without a valid number (`XNaN`, `XInf`, `X-`, `X.`, `X1.2.3`) = `INVALID_NUMBER`; any other character (`#`, `[`, `=`: macros, expressions) = `UNEXPECTED_CHARACTER`. Because of the exponent rule an `E` word straight after a number (`X1E5`) is read as an exponent, which is intended (routers have no E axis). A UTF-8 byte order mark at the start of the file is stripped with an informational `BOM_STRIPPED` warning (nothing is silent); a BOM anywhere else is `UNEXPECTED_CHARACTER`. CRLF, LF and bare CR all split lines; `lineEnding` reports `crlf | lf | cr | mixed | none`, so the post's line-ending rule can be checked.
- **A line with an error changes nothing** (not executed, `skipped: true`), like a controller rejecting the block; reading goes on so every error is reported. Exception: an arc whose geometry fails (radius mismatch, bad R) still moves the position to its well-defined end point so later lines are read correctly; no move is emitted for it.
- **Modal machine (RS-274 order inside a line):** units → F → S → T → M6 → M3/M4/M5 → M7/M8/M9 and extra M codes → plane/distance/arc distance/work offset → G4 → motion → M0/M1/M2/M30. Units come first so every number of a line is read in that line's units. Supported: G0–G3, G4 (P or X), G17, G20/G21, G90/G91, G90.1/G91.1, G54–G59, G40, G49, harmless G61/G64/G80/G94, F, S, T, M0/M1/M2/M3/M4/M5/M6/M7/M8/M9/M30, N (block number, warning if not first), O (ignored).
- **Defaults and `explicit`:** before the program sets them the reader assumes G21, G90, G17, G54 and arc distance `options.arcDistanceDefault` (default **G91.1, incremental**, the Mach3 and LinuxCNC default). `state.explicit.{units, distance, arcDistance, plane, wcs}` records whether the program set each group itself, so T019 can enforce §7.2 rule 1 (assume no modal state) instead of the reader guessing.
- **Errors (geometry the reader cannot model; reading on would give a wrong path):** G18/G19 = `UNSUPPORTED_PLANE`; G10, G12/G13, G15/G16, G28, G30, G38.2, G41/G42, G43, G51, G52, G53, G54.1, G68, canned cycles G73/G76/G81–G89, G92.x, G93, G95, M47, M98, M99 and non-integral code numbers (G0.25) = `UNSUPPORTED_CODE`; two codes of one modal group in a line (G0 G1, G20 G21, M3 M5, M9 with M7/M8, G4 with a motion code) = `MODAL_GROUP_CONFLICT`; a value letter twice = `DUPLICATE_WORD`; F ≤ 0, S < 0, non-integer T, G4 without a time or with a negative one = `INVALID_VALUE`; G4 with P and X or with other axis/arc words = `AXIS_WORD_CONFLICT`; axis words before any motion mode = `NO_MOTION_MODE`; empty program (no words at all) = `EMPTY_PROGRAM`.
- **Strict mode (default, PO decision on PR #24):** the reader is a safety layer, so **any G or M code it does not model and any letter it does not understand (A, B, C, E, H, L, Q, U, V, W, …; e.g. G61.1, G7, M10) is an `UNKNOWN_WORD` error** and the line is not run (an M code becomes known through `options.extraMCodes`). Modelled no-ops are accepted: G40, G49, G61, G64, G80, G94, and O (program number). `options.strict: false` downgrades only `UNKNOWN_WORD` to a warning and ignores the word (the rest of the line runs), for reading foreign sample files such as the owner's Mach3 programs at field test; it never relaxes the other errors (unsupported codes, plane, numbers, arcs) and must not be used for export checks. `gcodeIssueSeverity(code, strict)` gives the severity.
- **Units:** G20 converts X/Y/Z/I/J/K/R and F to mm (× 25.4) and warns `INCH_UNITS` once. F is stored in mm/min; a later G21 without a new F keeps the converted value.
- **Position:** starts at `options.initialPosition` (default 0, 0, 0), every axis flagged in `assumedAxes` until the program sets it absolutely; each move carries the assumed axes of its end point (rule 2, "first move to safe Z", needs this). An incremental move on an assumed axis warns `INCREMENTAL_FROM_UNKNOWN` and the axis stays assumed. An arc starting from an assumed X or Y = `ARC_FROM_UNKNOWN_POSITION` error.
- **Feed:** modal. A G1/G2/G3 with no F defined yet is **not** an error: the move gets `feed: null`, a `missingFeed` event and a `FEED_UNDEFINED` warning; T019 judges it (rule 5). Every move has `feedExplicit` (F written on that line). Rapids have `feed: null`.
- **Arcs (G17):** I/J in the active arc distance mode (a missing one = 0) (kept after the tester review, O3: standard RS-274 behaviour, the posts always write both), or R. Both R and I/J, or neither, = `ARC_INVALID`. I/J: start and end radius differing by more than `options.arcTolerance` (default `ARC_RADIUS_TOLERANCE` = 10 × EPS = 0.01 mm: enough for 3-decimal output, far below a visible error) = `ARC_RADIUS_MISMATCH`; zero radius = `ARC_INVALID`; start = end (within EPS) = full circle (sweep 2π). R: **R > 0 = the arc of at most 180°, R < 0 = more than 180°** (centre right of the chord for G2 R+ / G3 R−, left otherwise); a full circle with R, R = 0, or a chord longer than 2|R| + tolerance = `ARC_INVALID` (within the tolerance it is a half circle). A Z change makes the arc helical. Each arc move has `arc { cx, cy, radius, sweep ∈ (0, 2π], direction, form }`. `sampleGcodeMove(move, chordTolerance = 0.01)` splits arcs into equal steps with chord error ≤ the tolerance for consumers; `gcodeMoveLength` gives the helical length.
- **Events** (each with `line` and `moveIndex` = index of the next move, so the order against moves is exact): `spindle` (M3/M4/M5, and an S change while running), `dwell` (seconds), `toolChange` (M6 with the selected T; M6 without a T warns `TOOL_CHANGE_WITHOUT_T`, tool null), `pause` (M0; M1 `optional`), `coolant` (M7 mist, M8 flood, M9 off; the posts map vacuum to these), `mcode` (codes in `options.extraMCodes`, for machine-specific vacuum codes), `missingFeed`, `end` (M2/M30). T alone only selects (`state.selectedTool`); `tool` changes at M6. **M3/M4 while no S was ever set warns `SPINDLE_NO_RPM`** (the move still reports `rpm: null`; T019 judges rule 4).
- **Dwell:** `G4 P` in `options.dwellUnit` (default **seconds**, Mach3/LinuxCNC; `ms` for Fanuc-style controllers), `G4 X` always seconds (Fanuc convention).
- **Program end and markers:** after M2/M30 further code is not executed (`CODE_AFTER_END` warning once); no end code = `NO_PROGRAM_END` warning (rule 7 is T019's). After the second `%` everything is ignored (`CONTENT_AFTER_END_MARKER`). **A lone `%` after code and before the end, followed by more code, warns `PERCENT_MID_PROGRAM`** (some controllers stop at a `%`); a leading `%` and a closing `%` after M30 are fine. Block delete lines are skipped by default (`options.blockDelete: 'execute'` runs them), both with a `BLOCK_DELETE` warning (the result depends on the operator's switch).
- **Snapshots:** `lines[]` has one entry per physical line: `line`, `block` (N), `comments`, `skipped`, and a copy of the modal state after the line (motion, plane, units, distance, arc distance, wcs, explicit flags, feed, rpm, spindle, tool, selected tool, coolant, position, assumed axes, ended). `options.snapshots: false` turns them off for very large files.
- **Comparison adapter (for T019):** `toComparablePath(moves) → { start, moves: ComparableMove[] }`, `ComparableMove { kind: 'rapid' | 'linear' | 'arc', x, y, z, cx?, cy?, direction?, feed, line? }`. Defined independently but with the toolpath model's field names (D-021), so T019 maps a toolpath move with `plunge → linear` and compares after the frame conversion. The reader itself never sees toolpath types.
- **Tests:** `reader.test.ts`: lexer cases; a Mach3-style program (CRLF, G91.1, M7 vacuum, M0 tool pause, G4 P, two-pass rounded rectangle), a Fanuc-style program (`%`, O, N numbers, leading-zero codes, no spaces, `;` comments, G90.1, T M06, G04 X), an inch program (G20 conversion and flag); both arc forms (I/J incremental, I/J absolute, R ± in both directions, full circle, helix), arc errors and tolerance; modal carry-over (feed, motion, plane), G91, assumed axes, events, missing F, code after M30, block delete; an error table (exponents, G18/G19, unsupported codes, group conflicts, duplicates, invalid values, NaN-like tokens), empty files, a bad line changes nothing, invalid options. `reader.property.test.ts` (fast-check): random valid programs from a small grammar (absolute G0/G1 with omitted axes and modal motion, G91 blocks, G2/G3 in I/J incremental, I/J absolute or R form, random case, compact or spaced, CRLF or LF): read endpoints equal the generated ones, consecutive moves chain, arcs radius-consistent and on the generated centre, sampled points on the circle, comparable path = read endpoints; determinism; a 1000-run fuzz (never throws, finite coordinates, `ok` ⇔ no errors). Mutation check: flipping the R sign convention is caught. `reader.perf.test.ts`: 100 000 lines (lines, I/J and R arcs, comments, CRLF) with snapshots in ≈ 0.45 s locally (limit 2 s). `arc.test.ts`: sampling, lengths, adapter. `independence.test.ts`: see above. `golden.test.ts`: every golden file of the post processor on main (`packages/machines/*/v1/golden/*.nc|*.tap`, generic + Mach3, 6 files, read as data, not imported) reads in strict mode with 0 errors and 0 warnings, CRLF, ends with the spindle off, units/distance/plane/wcs explicit, every feed move with a feed and the spindle on. Strict-mode tests: unknown letters and codes are errors and the line is not run; `strict: false` turns exactly those into warnings and relaxes nothing else.
- Revisit: canned cycles (G81/G83) and cutter compensation if a post ever emits them (§6.4 "delik döngüsü"), G18/G19, G43 with tool lengths from the profile, dwell unit and vacuum M codes passed from the post config / profile by T019 (`dwellUnit`, `extraMCodes`).

## D-027 Automatic G-code checks and the export gate (2026-11-17, T019)

- **API:** `checkGcode(text, context) → { ok, violations [{ rule, code, severity, line, message }], summary }`; `checkGcodeFiles(files, context)` for an export (the files of one sheet consume that sheet's operations in order: split programs and "none" mode files; the layout is checked over all files of a sheet; a sheet without a file = `SHEET_MISSING`); `canDownload(result)` = no error violation (the T021 gate); `expectedLayout(project, sheet)` / `expectedLayouts(project)`. `ok` is false on any error-severity violation. Rule ids: `R1`–`R10` (§7.2), `MODEL` (read path ≈ model), `LAYOUT` (part count/positions), `TOOLS` (tool-change order/numbers), `INPUT` (unusable context: never a pass). Each rule + code is reported once per file (first occurrence).
- **Context:** profile + verification state of the profile version, the post's **declared expectations only** (`GcodeCheckPostExpectations`: status, dwell unit, arc distance word, chord tolerance, tool-change mode and first-tool pause, vacuum on/off, decimals → tolerances; a `PostConfig` fits structurally, no generator code), the expected toolpath (sheet frame), stock (thickness, sheet size), sheet, operations (default: all of the sheet) and the expected parts. The spoilboard allowance comes from the profile. A toolpath target depth ≠ −(thickness + allowance) is `INPUT/STOCK_MISMATCH`.
- **Reader use:** `readGcode` in strict mode (never `strict: false`), dwell unit from the post, vacuum M codes other than M7/M8/M9 as `extraMCodes`. The read moves are used directly rather than `toComparablePath`: the checks also need each move's assumed axes, spindle, tool and arc sweep.
- **Lint boundary (why the checks may read the model):** `gcode-check/**` may import the reader, the toolpath model (the expected reference: §6.5 requires comparing the read path with the toolpath model and the layout), machine/schema types and geometry. It must not import `post/` (any spelling), the core barrel (`..`, `../index`, which re-exports post), `@nittcam/*`, absolute paths, or use dynamic `import()` / `require()` / `import()` types. Test files (`*.test.ts`, `*.testing.ts`) are exempt: they drive the generator to produce input. `independence.test.ts` follows every relative import of the check code transitively (TypeScript parser) and requires that nothing reached lies in `src/post/` or is the barrel; it also probes the ESLint rule with `lintText`. The frame conversion is written again here (`frame.ts`, inverse direction, from the profile fields), so a frame bug in the generator cannot cancel itself out.
- **Inverse frame:** `x = sx·X − sheetX`, `y = sy·Y − sheetY`, `z = Z − (thickness if Z zero = table)`; `sx`/`sy` = +1 when +X points right / +Y back; `sheetX` = offset.x (zero on the left) or −(offset.x + width) (zero on the right), the same for Y with front/back; one mirrored axis swaps cw/ccw. Hand examples = the D-025 worked examples (all four corners, an axis pointing away from the table, both Z references).
- **Checks** (heights in the sheet frame; safe Z = max(profile safe Z, toolpath safe Z); clearance = the toolpath's):
  - R1: units, distance, plane and work offset set explicitly before the first move (state snapshot of that line); the declared arc distance word as well (generic declares none: the D-025 exception, no violation); every move runs in G21/G90 (and the declared arc word): `MODAL_NOT_EXPLICIT`, `MODAL_WRONG`.
  - R2: the first move is a Z-only rapid up to safe Z (`FIRST_MOVE_NOT_SAFE_Z`); a rapid that changes XY (or sets a never-set X/Y) starts and ends at safe Z (`XY_RAPID_BELOW_SAFE_Z`); tool changes and pauses at safe Z (`TOOL_CHANGE_BELOW_SAFE_Z`); **the first move after a tool change or pause is a Z-only rapid to safe Z** (`NO_SAFE_Z_AFTER_TOOL_CHANGE`: the change macro or the operator may have moved Z, D-025; found by the mutation property, deleting that line was not caught before); no cut from a never-set position (`FEED_FROM_UNKNOWN_POSITION`).
  - R3: a rapid may not end below the clearance plane (`RAPID_BELOW_CLEARANCE`) or at/below the material top (`RAPID_INTO_MATERIAL`), except a straight retract upwards; a descending cut that ends below the material top runs at most at the plunge feed of the operations with the active tool, + the feed tolerance (`PLUNGE_TOO_FAST`).
  - R4: at every cut the spindle is on (M3; M4 = `SPINDLE_DIRECTION`), S > 0 within the profile range, the dwell since the last spindle start ≥ the warm-up (`CUT_SPINDLE_OFF`, `SPINDLE_NO_RPM`, `SPINDLE_RPM_RANGE`, `WARMUP_MISSING`), and the vacuum is on when post and profile switch vacuum (`VACUUM_NOT_ON`: an unheld part is a hazard; filed under R4 = machine ready before cutting).
  - R5: no cut with an undefined feed (`FEED_UNDEFINED`); the first cut after a rapid writes F (`FEED_NOT_EXPLICIT`).
  - R6: every end point and every arc's quadrant extremes within the travel, measured into the table from program zero, and Z between the spoilboard allowance below the table and the Z travel above it (`OUT_OF_ENVELOPE`, `BELOW_SPOILBOARD_ALLOWANCE`); the sheet footprint fits the table (`SHEET_OUTSIDE_TABLE`); cuts below the material top stay within the sheet + tool radius (`CUT_OUTSIDE_SHEET`). XY limits (envelope, table) allow half a unit of the written decimals (rounding); **Z limits (spoilboard depth = target depth, Z travel) have no tolerance** beyond 10⁻⁹ mm of float noise. The property test found a generated depth −3.1635 written as −3.164, 0.0005 mm below the allowance; fixed at the root (PO decision): the post rounds Z toward +Z (D-025).
  - R7: the program ends at safe Z, spindle off, vacuum off, M30/M2 after the last move, no code after the end (`END_NOT_AT_SAFE_Z`, `END_SPINDLE_ON`, `END_VACUUM_ON`, `END_CODE_MISSING`, `END_BEFORE_LAST_MOVE`, `CODE_AFTER_END`).
  - R8: reader `EXPONENT_NUMBER` / `INVALID_NUMBER` → `NUMBER_FORMAT`. R9: every reader error (with its own code); the reader warnings `BLOCK_DELETE` and `PERCENT_MID_PROGRAM` are errors (the result depends on the operator or controller), other warnings not judged by a rule stay warnings. R10: when the verification state is not `verified`, the profile is an example, or the post is not (known to be) `verified`, the first non-empty line must be a comment containing "DOĞRULANMADI … air cut" (Turkish letters folded).
  - TOOLS: model tools exist in the profile; auto posts: the M6 tool sequence equals the model's tool runs; M6 on a machine without an auto changer is refused; manual posts: pause count = runs − 1 (+1 with `pauseForFirstTool`) and the comment at each pause names exactly the expected `T<n>`; "none" posts: one tool per file; no tool change or pause with the spindle running; each cut's tool (when the program names it) = its operation's (`TOOL_MISMATCH`).
- **MODEL match:** the read path in the sheet frame against the operations' moves, in order. Rapid/plunge/linear = one read move of the same class ending at the same point (feeds equal). A model arc may be several arc pieces (sweep limit) or chords (arcs off): each piece keeps the centre, radius, direction, helix height and feed and progresses monotonically; an arc piece sweeps exactly its progress; a chord's sagitta stays within the declared chord tolerance (default 0.01) + the tolerance; the last piece ends at the model end. A model move shorter than the tolerance may be absent. Extra read moves allowed: Z-only rapids to safe Z (start, after a tool change, end). The first divergence is reported (`MODEL_MISMATCH` with the expected and the read move), plus `RPM_MISMATCH`. Tolerances: position = max(0.002, 5·10^−decimals) (generic 0.005, Mach3 0.002; 0.005 without a post), feed = half a unit of the feed decimals (0.5).
- **LAYOUT match:** a through cut = the feed moves between two rapids reaching the target depth; its part loop = the longest stretch between two vertices at the deepest Z with the same XY (the final pass from its start point back to it; leads and ramps stay outside, tab rises keep XY); the loop's box centre (arc extremes included) = the outline's box centre (an outward offset grows the box by r on every side). Each expected part (`placedOutline` box centre) is matched once within 0.05 mm: `PART_COUNT`, `PART_POSITION`, `PART_MISSING`, `CUT_NOT_CLOSED`.
- **exportNc(project, profileVersion, post, options?):** buildToolpath → generateGcode with its `check` hook = `checkGcodeFiles` (violations become `CHECK_FAILED`, rule 9) → files only when everything passed (`stage: toolpath | post | check | done`; the check result is kept). Defence in depth: the files handed out are compared with the files the hook checked, anything else is checked again. Project name and revision come from the options (defaults "NittCam", 0); the stored export record is T021.
