## D-010 Project JSON schema v1 interpretations (2026-11-16, T004)
Zod schema in `packages/core/src/schema/` (exported from `@nittcam/core`), modelled on spec §9.2. Where the spec is silent:
- **Strict objects:** unknown keys are rejected (no silent data loss); new fields arrive through a schema version + migration step.
- **Rect parts:** `params {w, h, r}` is the source; `outline` is optional and treated as a cache that is never read (`deriveOutline(part)` recomputes it). `r ≤ min(w, h) / 2`. The derived outline starts at `(r, 0)` (or `(0, 0)` when `r = 0`), runs CCW, uses quarter arcs with bulge `tan(22.5°)` and drops zero-length straight edges.
- **Contours:** `outline` and each `inners[]` entry are vertex arrays, implicitly closed. At least 3 vertices, or 2 when one segment is an arc (a circle). Direction (outer CCW, inner CW) is the stored convention but is not enforced by the schema; normalisation is T006's job.
- **Holes:** discriminated by `type`; every hole has an `id` (string, unique within its part, PO decision) so commands can address it. pocket = `id, d, cx, cy, depth, tool`; through = `id, d, cx, cy, tool` (no `depth`, it comes from stock thickness + machine sacrificial allowance, §4.5); groove = `id, d, cx, cy, depth, grooveWidth, tool`. For a groove, `d` is the **centreline** diameter (the tool centre follows that circle) and `grooveWidth < d` is required (PO decision). `tool` is the tool number in the machine profile (integer ≥ 1, PO confirmed). Rules that need other data (depth < thickness, d ≥ tool diameter, groove width vs tool) are validation rules for later tasks, not schema rules.
- **Enums:** `nesting.mode` ∈ `minWaste | fastest | minToolChanges` (§6.2); `cutting.leadIn` ∈ `arc | line`; `cutting.direction` ∈ `climb | conventional`; sheet `grain` ∈ `0 | 90` (free-angle grain is out of scope, §2.5); placement `rot` ∈ `0 | 90 | 180 | 270`.
- **Settings (§4.8, not in the §9.2 summary; PO decision):** top-level `settings.dimensionMode` ∈ `cut | finished`, default `cut` (a missing `settings` or `dimensionMode` parses as `cut`). In `finished` mode entered sizes are finished sizes and the edge-band thickness will be deducted from the cut size; only the field exists now, the deduction is implemented later.
- **Templates:** `params` is a record of number | string | boolean; `overrides` is the list of field names the user changed by hand.
- **Cross-references** checked by the schema: unique part ids; unique hole ids within a part; each placement points at an existing part, `index < qty`, and each copy is placed at most once. The grain rotation rule is enforced by the nesting engine, not the schema.
- **Migration:** `MIGRATIONS[n]` upgrades raw JSON from v`n` to v`n+1`; `parseProject(json)` upgrades then validates and returns `{ ok, project } | { ok: false, issues: [{ path, message }] }` (paths like `parts[0].holes[1].d`); `migrate(json)` throws `ProjectSchemaError`. Missing, non-integer or future `schemaVersion` is rejected with a clear message.
- **Dependencies:** `zod` 4.6.7 (MIT) in core, `fast-check` 4.10.2 (MIT) as a core devDependency.

## D-011 Command layer design (2026-11-16, T005)
Code in `packages/core/src/commands/` (registry, `plate/`, `part/`) and `packages/core/src/validate/`, exported from `@nittcam/core`. Spec §5.1, §5.4, §8.1.
- **Command = definition object:** `{ name, area, description, aiTool, params (Zod), check?, apply(draft, params) }`. `params` is the single source for runtime validation and the AI tool schema. Params objects are strict (unknown keys rejected).
- **Pure apply:** `applyCommand(project, name, params)` parses params, runs the optional precondition (`check`, e.g. duplicate part id), applies the recipe through Immer `produceWithPatches` and returns the new project plus forward and inverse patches. The input project is never mutated. The result is re-checked against `projectSchema`; a command that would produce an invalid project is rejected (`INVALID_RESULT`), so the stored project is always schema-valid. Rejections return `{ ok: false, error: { code, message, issues } }` and change nothing; codes: `UNKNOWN_COMMAND`, `INVALID_CONTEXT`, `INVALID_PARAMS`, `PRECONDITION_FAILED`, `INVALID_RESULT`.
- **Immer:** `immer` 11.2.9 (MIT, pinned; 11.2.10 was under two weeks old, D-008 rule). Core uses a private `new Immer({ autoFreeze: true })` instance so it never changes the global Immer config; `enablePatches()` is called once at module load. Projects returned by commands are frozen.
- **No clock in core:** the caller passes `{ actor: 'user' | 'ai', at }` with every command; `at` must be an ISO 8601 date-time with offset (validated by regex, not parsed). The log entry is `{ command, params, actor, at }` where `params` are the **parsed** params (defaults filled in), so replaying the log is deterministic.
- **CommandStack:** holds the current project, undo and redo stacks of `{ entry, patches, inversePatches }`, the append-only log and the current validation list. `execute` / `undo` / `redo` / `canUndo` / `canRedo`. Executing after an undo clears the redo stack. A rejected command touches nothing. Undo/redo are not log entries yet (open question; the `project_commands` table is T008+).
- **Ids are supplied by the caller** (`addPart.id`); core never generates random ids. `addPart` creates a rect part, appends it to `parts`, defaults: `name ''`, `qty 1`, `grainLock false`, zero edge band; inners/holes/templates empty. `addPart` params mirror the part JSON (`params: { w, h, r }`) so the `r ≤ min(w,h)/2` refine is reused.
- **Validation (rules, not schema):** `validateProject(project)` returns `{ code, severity, path, message }[]` and runs after every execute, undo and redo. The schema stays permissive (D-010). Rules now:
  - `PART_LARGER_THAN_SHEET` (error): rect part fits the raw sheet neither as is nor, when `grainLock` is false, turned 90°. Margin/gap are nesting concerns and not counted. Freeform parts are skipped until the arc-aware bbox (T006).
  - `HOLE_DEPTH_NOT_BELOW_THICKNESS` (error): pocket **and groove** depth must be `< stock.thickness` (§4.5). The "too close" warning needs a threshold the spec does not give (open question).
  - Hole diameter / groove width vs tool diameter (§4.5) is **not implemented**: the project has no tool table yet; it comes with the machine profile (T010).
- **AI tools:** `commandToolDefinitions()` returns `{ name, description, inputSchema }` for every command with `aiTool: true`, using `z.toJSONSchema(params, { io: 'input' })` (fields with defaults are optional). Refinements are not in the JSON Schema; `applyCommand` enforces them. Export and machine-profile editing are never AI tools (§5.4); `setMachine` only selects a profile and is allowed.

## D-012 Geometry core: bulge polyline (2026-11-16, T006)
Code in `packages/core/src/geometry/` (`constants`, `types`, `segment`, `polyline`, `transform`), exported from `@nittcam/core`. Spec §6.1, §4.4.
- **One vertex model:** `Vertex` is the schema type (`{x, y, bulge}`, D-010). `Polyline = { vertices, closed }`; `contour(vs)` wraps a stored (implicitly closed) contour. Segment i runs from vertex i to i+1; bulge = tan(θ/4), θ signed sweep, + = CCW. In an open polyline the last bulge is ignored.
- **Tolerances:** `EPS = 0.001` mm and `JOIN_TOL = 0.05` mm in `geometry/constants.ts`. One more constant, `MIN_BULGE = 1e-9`: smaller bulges are lines (sagitta < 5 nm on a 10 m chord; avoids a huge, imprecise circle). A zero-length chord is always a line. Core had no other magic tolerances to replace.
- **Segment helpers:** `arcOf` (centre, radius, start angle, sweep), `segmentMidpoint` (via the sagitta, no trig), `segmentLength`, `segmentArea`, `segmentBBox`, `sampleSegment`, `bulgeToSweep`/`sweepToBulge`.
- **Area:** exact for arcs: shoelace over chords plus r²(θ − sin θ)/2 per arc (series for |θ| < 0.01 to avoid cancellation). An open polyline is measured as if closed by a straight chord.
- **Orientation:** `'ccw' | 'cw' | 'none'`; |area| ≤ EPS² mm² is `'none'`. `normalize(poly, 'outer' | 'inner')` gives CCW/CW; open and degenerate polylines are returned unchanged (a copy).
- **Reverse:** a closed polyline keeps its start vertex (v0, vn−1, …, v1); each segment's bulge is negated and moved to the segment's new start vertex. For open polylines the ignored last bulge is carried along so reversing twice is the identity. Negation uses `0 − v` so no `−0` appears in output.
- **bbox:** endpoints plus the arc's axis extremes (0°, 90°, 180°, 270°) inside its sweep. Throws `RangeError` on an empty polyline.
- **Transforms:** `translate`, `rotate(poly, 0|90|180|270)` about the origin by swapping/negating coordinates (exact, no sin/cos), `mirror(poly, 'x' | 'y')` where `'x'` negates x (left-right flip) and `'y'` negates y. Mirroring negates bulges and flips orientation; it does not re-normalise (call `normalize`). `transform(poly, { mirror?, rotate?, dx?, dy? })` applies mirror → rotate → translate.
- **Closing (§4.4):** `isClosed` = flagged closed, or open with ≥ 3 vertices and ends within JOIN_TOL. `close` drops the duplicate end vertex (the previous segment now ends at the first vertex, bulge kept) and sets `closed: true`; a larger gap returns the open copy unchanged so the caller can warn "kesilemez, kapalı değil".
- **Wiring:** `PART_LARGER_THAN_SHEET` now covers freeform parts with the arc-aware bbox of `outline` (path `parts[i].outline`) and compares sizes with EPS slack (a bbox from arcs can overshoot an exact fit by rounding; rect parts get the same slack). Message sizes are rounded to 3 decimals. Margin/gap stay out (T012). `rectOutline` treats `r < EPS` as sharp corners (not machinable) and uses `sweepToBulge` for `QUARTER_ARC_BULGE`.
- **Tests:** unit tests per helper and fast-check properties on rectangles, rounded rectangles and convex polygons with bulges in [−0.15, 0.4] (inward arcs limited so they cannot cross at a ≥ 36° corner).

## D-013 Offset: our own TypeScript implementation (T007, PO decision, 2026-11-16)
Evidence: `docs/spikes/T007-offset.md`. Chosen: **C, our own arc-preserving offset in `packages/core/src/geometry/offset.ts`**.
- Why: as accurate as CavalierContours on every fixture and on 9 987 random contours (max deviation 2e-13 mm on fixtures); arcs stay bulges, so G2/G3 come out directly; 3.6 kB gzip, no runtime dependency, no second language (§8.4); does not inherit the 4 defects found in `cavalier-contours-js`. Clipper2 rejected: arcs come back only approximately (deviation above EPS) and its main repo is archived. Building Rust CavalierContours to WASM ourselves was rejected because it adds a second toolchain.
- `cavalier-contours-js` stays as a **devDependency test oracle only** (never in the bundle).
- API: in core, `offset(poly, d)` with d > 0 = right of travel. With stored orientations (outer CCW, inner CW), `+toolRadius` gives the tool-centre path for both. The toolpath layer (T014) exposes outer/inner semantics.
- `ARC_COLLAPSED` (corner radius < tool radius): a warning, surfaced to the user as a validation warning (§4.4) by the toolpath layer.
- `SPLIT` on an inward offset of an **inner contour or hole** is an **error that blocks export** (the tool cannot pass the neck, so the part stays attached). Implemented in the toolpath layer (T014). Safety first (§7).
- Known limits: single closed non-self-intersecting contour, no islands, worst case O(n²) (2000 segments ≈ 130–320 ms).
- Revisit triggers: pocket/island offsets, DXF contours with 1000+ segments, or a defect in C we cannot fix quickly.

## D-019 Rectangle placer, min-waste mode (2026-11-17, T012)
Code in `packages/core/src/nesting/` (`bins`, `nest`, `fit`, `tool`, `types`, `__bench__/`), the commands in `packages/core/src/commands/nesting/`, the size rule in `validate/`, and `apps/web/lib/nesting.worker.ts` + `use-nesting-worker.ts` + the parts page panel. Spec §6.2, §8.2, §5.1, §5.4.
- **Spacing formula:** spacing `s = (toolDiameter + gap) / 2`. Every part's bounding rectangle is inflated by `s` on each side for collision checks, so two parts are always at least `toolDiameter + gap` apart (each cut takes a kerf of one tool diameter around its part, plus the configured gap). The usable area is the sheet shrunk by `margin` on every side: `[margin, width − margin] × [margin, height − margin]`; a part (not inflated) must lie inside it. The packer works in a bin of `usable grown by s` (`x, y = margin − s`, `w = width − 2·margin + 2s`, `h = height − 2·margin + 2s`), so "inflated part inside the bin" ⇔ "part inside the usable area". The margin is therefore measured from the sheet edge to the part edge; the tool may run into the margin. Fits are accepted within `EPS` (0.001 mm), so separations and edges hold within EPS.
- **Tool diameter:** passed by the caller (`runNesting { toolDiameter }`, 0 < d ≤ 50 mm, same bound as the profile). `nestingToolDiameter(profile, stock)` picks the suggested tool of the profile's material set with the same material and thickness, else the largest flat/compression end mill, else the largest tool. The draft parts page uses the example profile (MDF 18 → T2, 8 mm) until the wizard selects a machine (T023).
- **Placement coordinates:** `(x, y)` is the bottom-left corner of the part's bounding box **after** rotation, in sheet coordinates (origin bottom-left, Y up). Rotation is about the part's local origin, CCW; the toolpath layer rotates the outline and translates its rotated bbox minimum to `(x, y)`. The placer emits `rot` 0 or 90 only (for a rectangle 180/270 have the same footprint); locked placements may carry any of the four.
- **Grain:** `grainLock` parts are never turned 90° (rot 0 only from the placer); free parts try 0 and 90 (squares only 0). The rule is relative to the sheet frame, so sheet `grain` 0/90 does not change it.
- **Algorithm:** own MaxRects (Jylänki; free list of maximal rectangles, split on placement, new pieces pruned against containing ones) with best-short-side-fit, best-area-fit and bottom-left, plus a guillotine bin (disjoint free rectangles, shorter-leftover-axis split) with best-short-side-fit and best-area-fit. Orderings: area, longest side, perimeter (w + h), height, width, all descending, ties by part id (code-unit order) then copy index. 5 orderings × 5 heuristics = 25 candidates. Each candidate packs copies in order, first-fit across open sheets (the best position on the first sheet that has one), and opens a new sheet otherwise. Freeform parts use the arc-aware bounding box of their outline (true-shape nesting later, §6.2).
- **Objective (§6.2):** `min(A_waste + λ·L_cut + μ·N_toolchange + ν·C_handling)`, weights `{ waste, cutLength (λ), toolChanges (μ), handling (ν) }` in `MODE_WEIGHTS` per mode, overridable per call. Only `A_waste` is measured now; L, N, C are 0 until the toolpath exists (T014+), so all three modes rank like min-waste for now and λ/μ/ν are placeholders. **A_waste** = for every sheet but the last, sheet area − part area; for the last sheet, the used strip − part area, where the used strip is the smaller of the full-height strip up to the rightmost part edge + s and the full-width strip up to the topmost part edge + s (the rest stays a reusable offcut). Candidates compare lexicographically: fewer unplaced copies, then fewer sheets, then lower objective; the earlier candidate wins a tie.
- **Locked placements:** `layout.sheets[i].placements[]` with `locked: true` stay on their sheet, unchanged and first in the sheet's list; they are inflated obstacles for the bins. Unlocked placements are recomputed. Sheets up to the last one holding a locked placement are kept (an earlier sheet without locked parts is filled like a new one). A locked copy is not placed again.
- **Unplaced:** a copy that fits the usable area in no allowed orientation is `TOO_LARGE` (checked before packing with the same rule as validation; packing is one pass per copy, so it always terminates). A defensive branch reports `TOO_LARGE` instead of leaving an empty sheet if a bin ever refuses an empty-sheet fit. Every input copy ends up placed once or unplaced once (property-tested).
- **Statistics:** part area = bounding-box area; sheet area = raw `width × height`; waste % per sheet and overall = 100 · (sheet area − part area) / sheet area; utilisation = 100 − waste. `summarizeLayout(project)` derives the same figures plus the copies with no placement from a stored layout (the UI uses it, so undo/redo update the numbers).
- **Validation:** `PART_LARGER_THAN_SHEET` now compares with the usable area (sheet − 2·margin) using the same `fitsUsable` rule as the placer, freeform parts by bbox (deferred from T005/T006). The message names the usable size and the margin.
- **Commands:** `setNestingOptions { mode?, gap?, margin? }` (at least one) and `runNesting { toolDiameter }`, both AI tools. The AI can run nesting but never passes placements (§5.4: the engine makes geometry). `runNesting` writes `layout` in one undo step; re-running with an unchanged result records nothing (`changed: false`).
- **Web Worker (§8.2):** `lib/nesting.worker.ts` runs `applyCommand(project, 'runNesting', …)` on the posted copy and returns `{ params, patches, inversePatches }` plus the summary. The page records them with the new `CommandStack.executeApplied(name, applied, context, basedOn)`: `basedOn` must still be the current project, otherwise `STALE_BASE` (the parts changed while nesting ran; the user re-runs); the patched project is schema-checked (`INVALID_RESULT`). So the placer runs once, off the main thread. The worker is created on first use and terminated on unmount.
- **Determinism:** no randomness, `Array.prototype.sort` (stable) with full tie-breakers, insertion-ordered free lists, first candidate wins ties; the result does not depend on the order of the input part list (property-tested, byte-identical JSON).
- **Benchmark:** `pnpm --filter @nittcam/core bench:nesting` (Vitest with `vitest.bench.config.ts`, not part of `pnpm test`) prints sheets, utilisation %, waste %, last-sheet use, winning strategy and median time for three datasets in `src/nesting/__bench__/datasets.ts`. Baseline (2026-11-17, 2800 × 2070, gap 8, margin 10, tool 8): kitchen cabinets 64 copies → 4 sheets, 75.28 %; shelf sets 27 copies → 2 sheets, 67.77 %; many small parts 300 copies → 2 sheets, 62.41 %. 200 random parts nest in well under 2 s in Node (≈ 40–100 ms).
- Revisit: when cut length / tool changes are measured (fill L, N, C and tune λ, μ, ν), offcuts first (§6.2, M4), best-fit across sheets or more heuristics if utilisation needs it, and true-shape nesting for freeform parts.

## D-021 Toolpath model: outer contour, multi-pass, leads, plunge, direction (2026-11-17, T014)
Code in `packages/core/src/toolpath/` (`types`, `build`, `path`, `lead`, `depth`, `safety`, `stats`). Spec §6.3, §6.1, §4.5, §7.1, §7.2; D-013, D-016, D-019.
- **Model:** `Toolpath { units: 'mm', frame: 'sheet', safeZ, clearanceZ, targetDepth, operations[] }`. An `Operation` (`outerContour` in M1) has the part/copy/sheet, tool number + diameter, rpm, feed, plunge feed, travel (`cw|ccw`), pass depths and ordered `segments` (`approach`, `leadIn`, one `pass` per depth, `leadOut`, `retract`). Moves: `rapid`, `plunge`, `linear`, `arc` (end point, centre `cx/cy`, `direction` cw = G2 / ccw = G3, `bulge`, feed). Every coordinate is absolute in the **sheet frame** (origin bottom-left, Z 0 = material top, negative down); a move starts where the previous one ended. No machine-origin or Z-zero conversion here (T017). An arc that changes Z is helical (ramps only). `operationMoves(op)` flattens the segments.
- **Tab hook (T015):** every pass is its own segment; the last one has `final: true`, so tabs are inserted into that move list only.
- **Outline in the sheet frame (D-019):** `deriveOutline` → normalised CCW → rotated about the local origin by `rot` → its rotated bbox minimum moved to the placement `(x, y)` (`placedOutline`).
- **Tool-centre path:** `offset(outline, +toolRadius)` (D-013). `ARC_COLLAPSED` → warning on the result. An outer offset that fails or is not exactly one loop → `OFFSET_FAILED` error. **Note:** an outward offset never collapses a convex corner (a rounded rectangle r 2 with tool r 3 gives corner radius 5, no warning); `ARC_COLLAPSED` on an outer contour comes from **concave** arcs smaller than the tool radius. Inner contours: hook `innerContourPath` (CW, `+toolRadius` into the opening): `SPLIT` → `INNER_SPLIT`, any `ok:false` → `INNER_OFFSET_FAILED`, both export-blocking. Inner contours and holes are **not cut in M1**: a part with them gets `INNER_CONTOURS_NOT_SUPPORTED` / `HOLES_NOT_SUPPORTED` errors (export-blocking instead of a file that silently misses features), plus the hook's errors.
- **Cutting parameters:** the profile's material set with the stock's material and thickness (`tool`, `feed`, `plungeFeed`, `rpm`, `stepDown` = pass depth), each overridable by `options.cutting`. None found and no complete override → `NO_CUTTING_PARAMS`. Tool not in the profile → `TOOL_NOT_IN_PROFILE`. Cut depth deeper than the tool's flute length → `DEPTH_EXCEEDS_FLUTE_LENGTH` (safety, the shank would rub). Non-positive or non-finite values → `INVALID_OPTION`.
- **Depth:** target = `−(thickness + zZero.spoilboardAllowance)` (§4.5). `n = ceil((total − EPS) / passDepth)` equal passes, pass i at `−total·i/n`, the last set to the target exactly (the EPS keeps 18.3 / 6.1 at 3 passes despite float rounding). Nothing goes below the target.
- **Start point:** the middle of the longest straight segment of the tool-centre loop (first one on a tie), away from corners; a loop without lines (circle) starts at its first vertex.
- **Direction:** CW spindle (M3) assumed. **Climb on an outer contour = CW travel around the part, conventional = CCW** (the offset loop is CCW; climb reverses it with `reverse`, which negates bulges so arcs keep their shape). Inner contours (later) are the opposite: climb = CCW.
- **Leads (§6.3):** `arc` = quarter arc of radius L tangent at the start point P on the waste side (lead-in from `P + L·n − L·t`, lead-out to `P + L·n + L·t`, n = outward normal, t = travel tangent); `line` = straight line of length L at 45° to the contour on the waste side; `none`. Default type = `project.cutting.leadIn`, L = tool radius. Clearance check: the lead's arc-aware box must lie inside the sheet rectangle extended by the contour's own path box (with margin 0 the contour itself runs outside the sheet); samples at most 0.05 mm apart must be outside every part, at least the tool radius (− EPS) from the own outline and at least the tool radius + 0.025 mm from every neighbour outline. The distance to an outline is 1-Lipschitz, so this half-step margin makes the neighbour check hold for the whole lead, not only at the samples (hardened after a 2 500-run fast-check flagged a lead close to a neighbour; the test checker's inside test for rounded rectangles was made exact at the same time). The own part gets no margin because the lead ends on the contour at exactly the tool radius. Fallback L, L/2, L/4, then no lead; warnings `LEAD_SHORTENED` / `LEAD_REMOVED`.
- **Plunge:** `straight` (default): plunge at the lead start to the first pass depth; deeper passes step down at P inside the existing kerf. `ramp`: plunge in the air to Z 0, lead-in at Z 0, then per pass a **zig-zag ramp** along the contour: forward over leg length L to half the step, back to P reaching the pass depth, then the full loop; so every pass starts at P. L = `length`, else `(step / 2) / tan(angleDeg)` (default 3°); clamped to the contour length with `RAMP_STEEPER`. **Every move that goes down in Z uses the plunge feed** (straight plunges and ramps); the cutting feed is never used going down.
- **Safe Z (§7.2 rules 2, 3; defence in depth):** each operation starts with a rapid at safe Z above the lead start, rapids down to the clearance height (default 2 mm above the material, clamped to safe Z with `CLEARANCE_CLAMPED`), plunges at the plunge feed, and ends with a rapid straight up to safe Z. XY rapids happen only at safe Z. `toolpathSafetyViolations` checks these rules plus the target depth, finite numbers, positive feeds and arc consistency on every build; a violation is a `SAFETY_VIOLATION` error (the post and reader check again).
- **Issues:** `{ code, severity, partId (null = project), message, copy?, sheet? }`; `ok` = no errors. Unplaced copies → `UNPLACED_COPIES` warning; nothing placed → `NO_PLACEMENTS` error.
- **Order:** by sheet, then placement order (simple and deterministic; the real cut order is T016).
- **Summary (approximate):** cut length = 3D length of feed moves (helical length for ramps), rapid length = rapids within a sheet (the first rapid of a sheet starts at an unknown position and is not counted), time = feed lengths / feed + rapid lengths / `rapidFeed` (default 10 000 mm/min, no acceleration, tool change or warm-up).
